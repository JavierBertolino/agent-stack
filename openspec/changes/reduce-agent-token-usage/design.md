## Context

The kit's product is agent behavior, and the resolver is the primary agent on
every delivery run. Measured today:

- `.opencode/agents/resolver.md` renders at 19,323 B (~4.8k tokens) and loads
  as the system prompt on every resolver turn; the neutral role is 18,412 B /
  392 lines.
- Roughly 7 KB of that role duplicates material that already exists in
  `.agent-stack/skills/*`: branch setup ≈ `git-delivery` step 1, mirror
  publication ≈ `git-delivery` step 2, implementation-PR steps ≈
  `git-delivery` step 3, task-status handling ≈ `linear-workflow` steps 3–4,
  verification contract and readiness gate ≈ `openspec-workflow` steps 4–5.
  §2 of the role already mandates loading exactly those skills before the
  corresponding action.
- The shipped role cites two paths that the installer never creates:
  `scripts/run-state.py` (the real entry point is `astack run-state`,
  `scripts/astack:147`) and `docs/PRODUCT_INTENT.md` (kit-only).
- No installed role or skill mentions `astack` anywhere — `grep` over
  `.agent-stack/` returns nothing — and the kit's `docs/` are never
  installed, so a consuming project has no CLI reference at all. The only
  complete one is the usage heredoc inside `scripts/astack`.
- The rendered OpenCode resolver's bash block is `"*": ask` with explicit
  allows for `openspec *`, `git *`, `gh pr *`, `gh repo *`, and `herdr *` —
  verified absent for `astack` — so the `astack run-state` examples D4
  introduces would prompt the user every time.
- `tests/test-skills.sh` caps skills at 500 lines and 1,024-char
  descriptions, but nothing bounds roles or rendered agents, which is how the
  resolver reached 19 KB.
- `scripts/doctor.sh:190-207` compares skill mirrors by hash only, so
  byte-identical copies visible to one host pass silently, while
  `adapters/opencode/adapter.md` claims the installer avoids that case.
- `ci.yml`/`release.yml` install `@fission-ai/openspec@latest` while every
  action is SHA-pinned; the CLI is used by `scripts/doctor.sh` presence
  checks and any future CLI-driven test.
- `setup.sh` (4,189 lines / 147 KB) is generated by
  `scripts/build-installer.sh`, which also regenerates the embedded
  `write_role_source` / `write_skill_source` heredocs inside
  `scripts/setup-agent-stack.sh` from the neutral sources. Nothing marks it
  as generated for review tooling, and `AGENTS.md` says "never hand-edit"
  without saying "never open it".

Constraints: neutral sources are authored once under `.agent-stack/`;
`scripts/setup-agent-stack.sh` must stay POSIX `sh`; install and upgrade stay
idempotent and human-owned files are never overwritten; four delivery roles
stay fixed; Python stays stdlib-only.

## Goals / Non-Goals

**Goals:**

- Cut the resolver's rendered prompt from 19,323 B to ≤ 14,900 B (measured
  plan landing 14,554 B) with no behavior change, by removing content that
  duplicates mandatory skills.
- Make every path named by a shipped role resolve inside an installed
  project.
- Give consuming projects an installed map of the `astack` CLI, and make the
  rendered resolver able to run the commands its prompt directs.
- Enforce prompt-size budgets in CI so growth is a test failure, not drift.
- Make skill-mirror behavior honest: correct docs, warn on duplicate
  visibility, and prove roots are written only for enabled hosts.
- Make generated artifacts review-safe and CI-installed tooling
  reproducible.

**Non-Goals:**

- No change to role contracts, handoff/report schemas, run-state schema, or
  the permission mechanism: D9 adds four scoped `astack` allow entries inside
  the existing OpenCode permission block, introducing no new permission kind
  and touching no other host's model.
- No new roles, and no reordering of the delivery pipeline.
- No behavioral/eval harness for host runtime integration (tracked
  separately; `tests/run.sh` documents that gap).
- No rewrite of resolver-owned authority sections (§0/§2/§12): the measured
  split lands at 14,554 B rendered, and reaching the originally targeted
  12,000 B would mean restructuring the text the split deliberately preserves
  — owned by a follow-up change.
- No release signing, SBOM, plugin/marketplace distribution, multi-OS CI
  matrix, or Markdown lint/link toolchain.
- No de-duplication of `docs/*.md` against skill bodies (human-facing
  documentation may legitimately restate procedure).
- No copied `--help` or flag tables inside any skill: `astack-ops` stays a
  subcommand map, and `scripts/astack` keeps the authoritative usage text.
- No blanket `astack *` allow, and no permission changes for hosts other
  than the OpenCode resolver block.

## Decisions

### D1. Remove duplicated text from the resolver; skills become the single source

Delete the duplicated procedure text from `.agent-stack/roles/resolver.md` and
leave a one-line pointer that names the mandatory skill from the existing §2
stage map:

| Resolver section | Destination |
| --- | --- |
| §3.1 Task status (1,004 B) | `linear-workflow` steps 3–4 (already there) — keep 2 lines: "use `linear-workflow` for assignee and state rules" |
| §4 Branch setup (1,361 B) | `git-delivery` step 1 — keep base-ref and stacked-PR decision rules |
| §5 artifact procedure + §5.2 + §5.4 (≈1,600 B) | `openspec-workflow` steps 3–5 — keep the gate as a one-line rule |
| §5.3 Traceability (1,041 B) | **moves into** `linear-workflow` (its only home today) |
| §6 Publication (1,086 B) | `git-delivery` step 2 — keep `SPECS_MODE` values and "failure blocks" rule |
| §11.2–§11.5 procedure detail (≈2,000 B) | `git-delivery` / `linear-workflow` — keep the closeout **sequence** (1, 6, 7, 8) and the run-state recording lines |

Keep in the resolver, because it must act without a skill load: §0 authority
rules, §1 intake, §2 stage-skill map, §3 clarify, §9 evidence review +
escalation menu, §10 QA gate, §12 operating contract, and the
`scripts/run-state`/`astack run-state` command examples (it is the sole
run-state writer).

*Alternative considered:* a new `.agent-stack/reference/*.md` tree — rejected.
Hosts have no discovery mechanism for it, so the resolver would have to guess
paths (the exact failure mode we are fixing), and it would add another eager
artifact to budget. *Alternative:* keep everything and only lower budgets —
rejected: the text is redundant, not just long.

### D2. Pointers use the existing mandatory-skill map, not new machinery

§2 already states which skill is mandatory at which stage and requires
recording name, resolved path/source, version, and why it was used. Pointers
added by D1 are ordinary sentences naming that skill, so no frontmatter,
permission, or manifest change is needed (resolver already has
`skill: allow`).

*Risk that drives this:* if a pointer is vague, the resolver skips the load
and loses the instruction. Every pointer therefore names the skill and the
section to apply, and no instruction may be removed without a destination
(the "no unguided search" requirement).

### D3. Budgets live in one new test, measured on a real install

New `tests/test-prompt-budgets.sh` (auto-discovered by the `tests/test-*.sh`
loop, no `run.sh` edit), with budgets declared as variables at the top:

- neutral role ≤ 400 lines; resolver ≤ 13,800 B — the measured plan landing
  (13,523 B) plus pointer headroom, with 13,800 + 1,031 B of frontmatter =
  14,831 ≤ the 14,900 B rendered cap, so the two budgets cannot disagree;
  every other role ≤ 7,000 B;
- rendered agent file ≤ 14,900 B (resolver) and ≤ 7,500 B (others), measured
  after a fixture `init --platforms opencode,claude,codex,cursor --mcp none`
  into `mktemp -d` — the pattern already used by `tests/test-equivalence.sh`;
- total eager skill descriptions ≤ 2,500 B (currently 1,167 B).

Budgets sit just above the measured plan landing for the resolver (~2–3%
over 13,523 B role / 14,554 B rendered — enough for pointer-wording variance,
tight enough that a landing materially off-plan fails) and well above current
measurements everywhere else (the tightest other role, mobile-qa, is ~13%
under its 7,000 B cap; skill descriptions are ~53% under theirs). The test
output prints measured vs budget so a bump
is a deliberate, reviewable diff.

*Alternative:* add checks to `test-skills.sh` — rejected: that file asserts
kit-side skill format, not rendered output, and mixing fixture installs into
it would slow every run that only needs format checks.

### D4. Path fixes point at the installed CLI, and a test keeps them honest

- Replace `scripts/run-state.py --root <project> …` with
  `astack run-state --root <project> …` in the resolver (keeping `--root` is
  required: `scripts/astack:147` prepends `--root "$PWD"`, and argparse keeps
  the last value, so an explicit project root still wins).
- Drop the `docs/PRODUCT_INTENT.md` pointer from the shipped role; kit intent
  stays kit-side for humans, and `.agent-stack/README.md` (already installed)
  is the on-demand entry point.
- `docs/RUN_STATE.md` keeps the kit-side invocation for kit developers and
  gains an "installed project" section naming `astack run-state`, so docs and
  role agree on what a consuming project runs.

New `tests/test-path-integrity.sh` installs the kit, then fails when any
repo-relative path in an installed role/skill is missing from the install
outside a declared allowlist of project-owned paths (`AGENTS.md`,
`CLAUDE.md`, `UX_AGENTS.md`, `UI_AGENTS.md`, `openspec/`, `reports/`,
`.agent-stack/config.conf`, `.agent-stack/runs/`). It also asserts that no
installed role contains `scripts/run-state.py` and that `docs/RUN_STATE.md`
and the role both name `astack run-state`.

### D5. Mirror dedupe = honest docs + a warning, not skipped roots

The obvious fix — don't write roots OpenCode would read twice — is rejected:
when Claude Code or Codex is enabled alongside OpenCode, that host *needs*
`.claude/skills/` or `.agents/skills/`, and OpenCode walks both. Skipping
them would break the second host. So:

- `render_skill_mirrors` keeps its per-`ENABLE_*` gating, and a single-platform
  install test proves no foreign root is created (it already holds; the test
  stops it regressing).
- `scripts/doctor.sh` gains a WARN when one skill is discoverable through
  more than one root of the same enabled host — including identical hashes —
  while differing hashes keep failing as today.
- `adapters/opencode/adapter.md` and `docs/ADAPTER_CAPABILITIES.md` are
  corrected to state the root mapping per host and that the residual overlap
  is expected, not a dedupe failure.

### D6. Generated artifacts: mark them, and forbid reading them

`.gitattributes` with `setup.sh linguist-generated`. *Alternative:* `-diff`
to hide it entirely — rejected, because local `git diff` after running
`build-installer.sh` is how a human verifies regeneration, and `--check` is
the real guarantee, not diff suppression. `AGENTS.md` gains one rule: never
open `setup.sh`; edit `scripts/setup-agent-stack.sh` (or neutral sources) and
regenerate with `scripts/build-installer.sh`. `tests/test-equivalence.sh`
extends its candidate list to installed `scripts/` outputs.

### D7. CI tooling pin moves into a manifest so dependabot can bump it

Add `package.json` + `package-lock.json` with `@fission-ai/openspec` pinned
exactly; both workflows run `npm ci` and expose `node_modules/.bin` on
`PATH`, replacing `npm install -g …@latest`. `.github/dependabot.yml` gains
an `npm` entry at `directory: "/"`.

*Alternative:* pin the version string directly in both workflows plus a guard
test forbidding `@latest` — rejected, because dependabot cannot read workflow
files, so the pin would decay into a manual chore. The honest risk today is
low (the CLI is used for `command -v` presence checks in `doctor`), but the
pin must not become a silent breakage once CLI-driven tests are added.

### D8. New `astack-ops` skill: a map that defers to `--help`

A new `.agent-stack/skills/astack-ops/SKILL.md` carries a one-line row per
subcommand (`init`, `sync`, `check`, `doctor`, `auth jev`, `jev ask`,
`update`, `upgrade`, `prune`, `run-state`, `validate`, `--version`,
`--help`) with the moment to use it, then states that
`astack <command> --help` is the authority for flags and syntax. Frontmatter
follows the house shape: `metadata.version` `"1.0"`,
`consumer: resolver, developer, web-qa, mobile-qa`, `stage: ops`; description
is ~160 B, which keeps total eager skill descriptions well inside the 2,500 B
budget (1,167 B used today).

*Alternative considered:* skip the skill and let agents run `astack --help` —
rejected, because the CLI surface spans setup, drift, upgrade, run-state, and
Jev, and trial-and-error discovery is the turn burn we are removing.
*Alternative:* paste the `scripts/astack` usage heredoc into the body —
rejected for the same drift reason as the resolver split: two copies of one
source.

**Registration ripple (deliberate, ~9 touch points):** new skill directory;
`SKILL_NAMES` (`scripts/setup-agent-stack.sh:40`);
`SKILLS`/`SKILL_MARKERS` in `scripts/build-installer.sh:29`;
`write_skills_manifest` and the installed-file list at
`scripts/setup-agent-stack.sh:3303`/`:3407`; `SKILLS` in
`scripts/doctor.sh:113`; the loop in `scripts/upgrade-agent-stack.sh:157`;
loops in `tests/test-skills.sh:31` and `tests/test-render-matrix.sh:56`;
`.agent-stack/skills/manifest.json`; `docs/SKILLS.md`.

**Prerequisite order:** `build-installer.sh:sync_skills()` locates each skill
by the literal start pattern `    <skill>) cat > "$target" <<'<marker>'` and
aborts with `block start not found` when it is absent, so the
`astack-ops) … SKILL_ASTACK_OPS_EOF` case arm in `write_skill_source` must be
hand-written first. Only the heredoc *body* is regenerated from the neutral
source afterwards, and `--check` must be run then.

### D9. Scoped `astack` allows, not a blanket `astack *`

Add four entries to the resolver case in `render_opencode`
(`scripts/setup-agent-stack.sh:1597`): `"astack run-state *": allow`,
`"astack check *": allow`, `"astack doctor *": allow`,
`"astack validate *": allow`. Those are read-mostly or already-locked
operations the prompt directs during normal delivery. `astack update`,
`astack upgrade`, and `astack prune` mutate the install or the project tree
and stay on the `"*": ask` default, so a human still approves them.

*Alternative considered:* `"astack *": allow` — rejected: it would silently
authorize install replacement and file pruning from inside an autonomous run,
which is exactly the class of side effect the existing allow list keeps
prompted (`git push` is allowed but merge is not; `gh pr` is scoped to
creation, not merge).

Other hosts need no change: Claude's resolver renders `tools` without `bash`
deliberately, Codex and Cursor run under their own sandbox modes, and
developer/QA roles already have `bash: allow` or `bash: deny`.

## Risks / Trade-offs

- [Resolver skips a load after text is removed] → pointers name the skill and
  section; §2 already makes those skills mandatory per stage; doctor reports
  missing skills; the "no unguided search" requirement is a spec scenario and
  an audit task maps every removed block to its destination.
- [A block is removed with no destination, silently changing behavior] →
  tasks require a section-by-section migration table checked off in
  `tasks.md`, plus the unchanged rendering/contract/equivalence suites.
- [Budgets cause churn on legitimate growth] → caps set just above measured
  values with the derivation recorded in the spec, budgets in one file with a
  comment, and a documented bump procedure; budgets fail loudly rather than
  silently.
- [New doctor WARN alarms single-host users] → severity WARN (not FAIL), with
  a message stating multi-host installs make this expected.
- [Adding `package.json` to a POSIX-sh/Python kit] → dev-only, locked, never
  shipped in the installed tree; kit scripts remain `sh` + stdlib Python.
- [Upgrade leaves existing projects on the old 19 KB resolver] →
  `ensure_role_sources` uses `copy_if_missing`, so the gain lands through
  `astack upgrade`'s three-way merge; an upgrade test confirms unmodified
  roles are replaced and edited ones surface conflicts.
- [`astack` not on PATH in some environments] → `doctor` already fails when
  `astack`/dependencies are missing, and the remediation text points at the
  install command.
- [One of the ~9 skill registration lists is missed, so `doctor`/`upgrade`
  disagree about `astack-ops`] → registration is a single task with a
  checklist of exact file:line anchors; `tests/test-skills.sh` fails when the
  manifest lacks a skill directory or vice versa, `doctor.sh` fails on an
  unknown skill, and `build-installer.sh --check` catches the embedded copy.
- [`astack-ops` body starts copying flags and drifts from `scripts/astack`] →
  the skill's own rule names `--help` as the authority; no flag table is
  written; `docs/SKILLS.md` documents skills as procedure maps, not CLI
  references.
- [The four new allow entries widen resolver capability] → they are scoped to
  run-state/check/doctor/validate, asserted by `tests/test-render-matrix.sh`,
  and `update`/`upgrade`/`prune` remain on `ask`; a blanket `astack *` is
  explicitly rejected in D9.
- [One more skill description pushes the eager budget] → +~160 B against
  1,167 B used and a 2,500 B cap, and `tests/test-prompt-budgets.sh` fails if
  it ever crosses.

## Migration Plan

1. Land D7 (CI pin) and D6 (`.gitattributes`, `AGENTS.md`, equivalence
   coverage) first — independent, low risk, and they protect later work.
2. Land D3 (budget test) in a **red** state, then D1/D2 to make it green:
   the failing budget is the forcing function that proves the split is real.
3. Land D4 (path fixes + integrity test) alongside D1, since both edit the
   resolver and its heredoc is regenerated together.
4. Land D8/D9 (the `astack-ops` skill, its registrations, and the scoped
   resolver allow entries) with D4 — the skill, the `astack run-state` wording,
   and the permission entries are one story: point at the CLI, document the
   CLI, authorize the CLI.
5. Land D5 (doctor warning + adapter docs).
6. Every role/skill edit is followed by `scripts/build-installer.sh`, then
   `build-installer.sh --check`, `sh tests/run.sh`, and a fixture
   `scripts/doctor.sh`, so the embedded heredocs and `setup.sh` never drift.
7. Rollback = revert the commits; no data, schema, or on-disk layout change
   is involved, and `astack upgrade` re-merges from the previous kit.
8. Consuming projects pick changes up via `astack upgrade`; the release notes
   entry calls out the prompt-size reduction, the new `astack run-state`
   wording and permission entries, the `astack-ops` skill, and the new
   doctor warning.

## Open Questions

- Final budget numbers are set from post-change measurements in the
  implementation PR (values in D3 are the proposal's targets, not measured
  results).
- Whether `docs/PRODUCT_INTENT.md` should instead be shipped under
  `.agent-stack/` for on-demand reading. Default is to drop the pointer; a
  follow-up can ship it if consuming projects ask for the rationale.
- Whether the duplicate-visibility warning should become a doctor `--strict`
  failure for hosts that can be configured to a single root.
